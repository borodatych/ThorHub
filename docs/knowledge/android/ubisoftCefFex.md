# Окно входа Ubisoft Connect под FEX на Thor

Лаунчер Ubisoft рисует окна встроенным Chromium (CEF): `upc.exe` — процесс браузера, `UplayWebCore.exe` — его подпроцессы
Оба 32-битные, поэтому на Thor их исполняет FEX через `libwow64fex.dll`

## Симптом

Окно входа открывается за 4–10 минут, буква появляется через секунды
Браузер грузит 2–5 ядер и за несколько минут вырастает до 6–8 ГБ
После «Log in» — ошибка «An error occurred while trying to send your request» или Android закрывает ThorHub из-за нехватки памяти

## Причина

Профиль simpleperf процесса страницы: основной поток ~73% времени проводит в самом FEX (`libwow64fex.dll`), а не в переведённом коде
V8 генерирует машинный код на лету, а пресет DENUVO включает `FEX_SMCCHECKS=full`
FEX на каждую запись в сгенерированный код выбрасывает и заново переводит блоки, кэш перевода растёт

Не причина (проверено замером):
Сеть — сервер входа `public-ubiservices.ubi.com` отвечает с Thor за 0,4 с
ntsync — с `PROTON_NO_NTSYNC=1` нагрузка та же
Журнал Wine — за 45 минут 0,8 МБ
Отрисовка — `--disable-gpu` не меняет ни память, ни нагрузку

## Что пробовали

| Режим | Окно входа | Вход |
|---|---|---|
| FEX, `SMCChecks=full` (как есть) | 4–10 минут, браузер 6–8 ГБ | ошибка отправки или убит по памяти |
| FEX, `SMCChecks=mtrack` на контейнер | 1 минута, память ровно 2,8 ГБ | кнопка крутится, запрос входа не уходит: сгенерированный JavaScript исполняется неверно |
| `mtrack` в `AppConfig/UplayWebCore.exe.json` | как `full` | переменная окружения `FEX_SMCCHECKS` сильнее файла на программу |
| `full` + V8 без JIT (`--js-flags=--jitless` у `UplayWebCore.exe`) | 2,7 минуты, браузер ~5,6 ГБ | перекомпиляции нет, но интерпретатор V8 в эмуляции не досчитывает вход и за 32 минуты |
| Box64 вместо FEX для 32 бит | лаунчер не запустился за 15 минут | — |

Флаги Chromium передавались правкой proton-wine `WINE_APPEND_ARGS` (дописывание аргументов программе по имени)
Механизм работал, но флаги не помогли, правка откатана
Отладчик (`--remote-debugging-port`) и сетевой журнал (`--log-net-log`) Ubisoft из своего CEF вырезала

## Грабли

Зависание на маленьком окне «Loading…» случается само по себе, в части запусков: по одному запуску нельзя судить о правке
Ввод через xtype доходит, но страница отрисовывает его с опозданием в минуты: не печатать в окно, пока идёт вход, — текст вклинится в поля
Настройки FEX на программу (`~/.fex-emu/AppConfig/*.json`) ThorHub переписывает при каждом запуске (`FEXCoreManager.ensureAppConfigOverrides`)

## Вход сохраняется только при видимом MAC

Лаунчер шифрует свои файлы `.vdat` (`user.vdat` с сессией, кэши настроек, прав и конфигурации): protobuf с MachineGuid, 12-байтовый nonce и шифротекст
Ключ, по всей видимости, строится из MAC сетевых адаптеров (`GetAdaptersAddresses`) — прямо это не проверено, код `upc.exe` обфусцирован
Android-патч сборки Proton (`android/patches/common/dlls_nsiproxy_sys_ndis_c.patch`) под `__ANDROID__` выключал `if_get_physical`: тип адаптера угадывался по имени, MAC оставался пустым
Итог: каждый запуск «Could not read user.vdat (error 6)», сессия не переживала перезапуск, и каждый раз требовался вход через тяжёлое окно
Ядро Android отдаёт приложению MAC по `SIOCGIFHWADDR` без ошибок — проверено нативным тестом в домене ThorHub
Правка proton-wine `c19de42`: `if_get_physical` вызывается и на Android, догадка по имени — запасная
После неё вход прошёл один раз (18.11.2026 16:54), а следующий запуск вошёл сам, без окна входа и без ошибок чтения `.vdat`

Проверочный приём: своя программа (mingw, `i686-w64-mingw32-gcc`) кладётся в папку игры, `executablePath` контейнера временно подменяется на неё, запуск обычным интентом — так проверяется любой API Wine без лаунчера

## Что осталось

Найти, почему `mtrack` ломает JavaScript V8 в wow64-режиме FEX — это путь к быстрому браузеру; вход теперь нужен один раз, поэтому это уже не блокер
